# ADR-001: Scope V1 as inline session-row attention routing

## Status

Accepted

## Date

2026-05-31

## Context

Atelier is evaluating a feature to help solo power users manage multiple local coding-agent sessions more effectively. The user problem is not broad observability in the abstract; it is fast attention routing. Users need to glance at the workspace and quickly decide which session or tab needs attention next.

Research showed that adjacent tools such as Claude Code Agent View, Cursor Agents Window, and community dashboards like guppi and agenttop all prioritize glanceable status and attention routing. At the same time, the codebase currently exposes only limited runtime truth: durable launch metadata and coarse terminal lifecycle signals such as exit detection. It does not yet support trustworthy active/idle/stale semantics.

Within Atelier, the cleanest existing UI seam is the expanded session row in the project sidebar. The most important model gap is that `WorkspaceTab` does not yet have durable per-tab agent identity, which limits mixed-agent session visibility and restore fidelity.

## Decision

Ship V1 as an inline attention-routing feature in expanded session rows.

The V1 scope will:

- add durable per-tab agent identity so mixed-agent sessions are represented truthfully
- show per-tab agent identity within expanded session rows
- use only trustworthy, low-ambiguity status signals in V1, such as launch identity, exit state, and recency-oriented signals
- avoid strong live-status claims such as active, idle, or stale unless the runtime can support them reliably
- defer a dedicated global Agents panel to a later phase

The main tab strip may reuse the same identity resolver in V1 only if that reuse is genuinely thin and does not materially slow delivery. It is not a required part of the accepted V1 scope.

## Alternatives Considered

### Alternative 1: Full monitoring surface in V1

- **Description**: Add inline visibility plus a dedicated global Agents panel with broader live monitoring semantics.
- **Pros**: Stronger competitive story, more obvious observability surface, broader long-term platform framing.
- **Cons**: Requires more UI surface area, higher semantic expectations, and pressure to invent runtime states the system cannot yet support reliably.
- **Why rejected**: Too large for the current learning goal and too risky given weak runtime instrumentation.

### Alternative 2: Heuristic-only inline visibility with no durable model changes

- **Description**: Show agent information in session rows using existing `launchCommand` heuristics only, without adding durable per-tab identity.
- **Pros**: Fastest path to something visible, avoids schema and persistence work.
- **Cons**: Mixed-agent sessions remain ambiguous, restore fidelity stays weak, and custom profile identity remains fragile.
- **Why rejected**: Too brittle for a feature whose value depends on trustworthy scanning.

### Alternative 3: Require tab-strip parity in the same V1

- **Description**: Ship the sidebar experience and main tab-strip agent identity together as one inseparable V1.
- **Pros**: Better cross-surface consistency and lower risk of split mental models.
- **Cons**: Increases execution scope and QA surface for the first learning release.
- **Why rejected**: Valuable if nearly free through shared reuse, but not important enough to block the first scoped release.

## Consequences

### Positive

- Focuses the release on the clearest power-user pain point: deciding where to look next.
- Improves truthfulness by grounding V1 in durable identity and defensible status signals.
- Preserves a fast learning loop without prematurely committing the product to a full observability surface.
- Creates a better foundation for future runtime-aware monitoring.

### Negative

- The initial feature will not fully satisfy users who expect true active/idle/stale monitoring.
- Some users may still want tab-strip parity immediately, creating pressure for a near-term follow-up.
- Schema and persistence work are required even for a focused UI outcome.

### Risks

- Users may interpret lightweight status as stronger truth than the runtime can support.
- Sidebar density may increase if row design is not carefully constrained.
- The feature may feel incremental if the surface does not materially reduce scan time.
- If the tab strip remains unchanged too long, product consistency may suffer.

## Implementation Notes

- Add durable per-tab agent identity before shipping the UI.
- Keep V1 status language factual or explicitly hint-like; avoid authoritative liveness claims.
- Prefer a shared identity resolver so future tab-strip or global-surface reuse does not fork the logic.
- Treat tab-strip rollout as optional thin reuse, not a hard requirement for the first accepted scope.
