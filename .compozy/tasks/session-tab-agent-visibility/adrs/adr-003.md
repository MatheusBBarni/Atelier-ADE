# ADR-003: Keep session-tab summary composition in AppShell

## Status

Accepted

## Date

2026-05-31

## Context

The PRD defines V1 as a focused inline navigator inside expanded session rows. The codebase already has durable tab identity and selection metadata in `WorkspaceTab`, plus an existing AppShell surface where `SessionRowView` can be extended. The remaining question is where the new session-tab summary composition should live.

The goal is to add the smallest viable technical surface that supports terminal-only inline rows, shared identity resolution, and direct tab selection without promoting this V1 into a broader monitoring subsystem.

## Decision

Keep session-tab summary composition in `NativeMacADE/AppShell` as a UI-scoped summary layer.

The implementation will:

- build session-row child summaries from `WorkspaceStore` state already available to the AppShell
- extract a shared presentation resolver in AppShell for agent label, icon, and terminal-title fallback logic
- use a lightweight observer source near `AppDependencyContainer` for terminal-exit fan-out rather than a broad new core status model
- avoid introducing a dedicated Core summary type or generic monitor service in V1

## Alternatives Considered

### Alternative 1: Core-owned summary model

- **Description**: Add a dedicated summary type and selector in `NativeMacADECore`, then have AppShell render that output.
- **Pros**: Stronger reuse across future surfaces and clearer separation between data selection and view code.
- **Cons**: Adds new core abstractions for a V1 surface that only one UI currently needs.
- **Why rejected**: The chosen scope is narrow enough that a UI-scoped summary layer is simpler and more reversible.

### Alternative 2: Broader monitor service

- **Description**: Introduce a generic runtime monitoring layer and build the sidebar feature on top of it.
- **Pros**: Better long-term foundation for a full agent-observability product.
- **Cons**: Adds significant architectural scope, encourages premature state semantics, and violates YAGNI for the approved V1.
- **Why rejected**: The product explicitly deferred a broader monitor surface and richer runtime status model.

## Consequences

### Positive

- Keeps V1 localized to the existing AppShell where the user-facing feature actually lands.
- Avoids new core abstractions and minimizes cross-package churn.
- Creates one shared resolver for terminal identity logic instead of duplicating sidebar and tab-strip heuristics.
- Preserves a reversible path if later research justifies a broader summary or monitor layer.

### Negative

- Summary composition remains presentation-local instead of reusable by default across all future surfaces.
- Some technical knowledge about tab identity resolution now lives in AppShell rather than only in Core.
- If additional surfaces need the same model later, refactoring may still be required.

### Risks

- View-local summary code could sprawl if the resolver and summary builder boundaries are not explicit.
- Exit-event fan-out could become ad hoc if it is implemented as callback chaining rather than a deliberate observer source.
- Future reuse pressure could push Core extraction later than ideal if V1 expands unexpectedly.

## Implementation Notes

- Place the shared presentation resolver close to `TabItemView`, `SessionRowView`, and `AgentProfileIconView`.
- Keep the summary layer terminal-only in V1.
- Use the observer source only for factual exit propagation; do not grow it into a generic runtime state bus.
