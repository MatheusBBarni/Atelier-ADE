# ADR-004: Use event-driven factual status derived from existing metadata

## Status

Accepted

## Date

2026-05-31

## Context

The approved PRD requires V1 to communicate only strictly factual status. The current codebase already persists identity and recency metadata on `WorkspaceTab`, and `TerminalHostController` emits terminal-exit callbacks. The remaining technical question is whether V1 should introduce new persisted or richer runtime status state, and how refresh should occur while the app is open.

The selected product posture favors truthfulness and low scope over richer but less reliable semantics.

## Decision

Use existing tab metadata plus ephemeral exit state, refreshed through event-driven updates only.

The implementation will:

- reuse `shortcutID`, `launchCommand`, `title`, `kind`, and `lastActivatedAt` already available on `WorkspaceTab`
- derive inline status from factual metadata and live exit observations only
- avoid persisting any new status snapshot fields
- avoid introducing a richer runtime status map in `WorkspaceStore`
- refresh inline rows only when tabs or selection change, restore completes, or a terminal-exit event is observed
- avoid timer-based refresh loops in V1

## Alternatives Considered

### Alternative 1: Persist a last-known status snapshot

- **Description**: Store a factual last-known status field per tab so the sidebar can always show stable status after relaunch.
- **Pros**: Stronger continuity after restore and less dependence on live observation.
- **Cons**: Expands the persistence contract for a narrow V1 and adds stale-data semantics to manage.
- **Why rejected**: The current product promise does not require persisted status, only persisted identity and factual navigation context.

### Alternative 2: Richer runtime status map

- **Description**: Add a first-class status model in `WorkspaceStore` for sidebar-facing runtime states.
- **Pros**: Cleaner central observation point and easier reuse across future surfaces.
- **Cons**: Encourages broader state semantics, adds store complexity, and exceeds the selected V1 scope.
- **Why rejected**: Too much structural cost for a release intentionally limited to factual status.

### Alternative 3: Timer-based refresh loop

- **Description**: Add a lightweight timer so recency text updates continuously while the app is open.
- **Pros**: More current-looking recency copy and less stale relative-time presentation.
- **Cons**: Adds background refresh behavior and complexity without improving the truthfulness of the underlying signal.
- **Why rejected**: Event-driven updates are enough for V1 and better match the approved scope.

## Consequences

### Positive

- Keeps the status model honest and easy to reason about.
- Avoids schema changes, timer loops, and a new runtime state machine.
- Makes it easier to test because updates come from explicit state transitions rather than continuous refresh.
- Aligns with the PRD’s requirement for factual rather than interpretive status.

### Negative

- Recency presentation will not stay continuously fresh unless another event triggers recomputation.
- Restored sessions cannot show a richer last-known status beyond current metadata.
- Users may see less expressive status than in competitor dashboards.

### Risks

- Users may interpret factual signals as stronger liveness than they really are.
- Event coverage gaps could make exit state appear inconsistent if not wired carefully.
- The limited model may create near-term pressure for a follow-up status phase.

## Implementation Notes

- Define one explicit mapping from factual inputs to sidebar row status presentation.
- Document that lack of an exit event does not imply running.
- Keep relative-time or recency wording conservative if no timer-based refresh exists.
