# ADR-003: Model continuity as a Focus Workspace sub-toggle

## Status

Accepted

## Date

2026-06-02

## Context

The approved PRD defines Focus Workspace Continuity as an opt-in extension of Focus Workspace rather than a separate workflow product. The codebase already persists `focusWorkspaceEnabled` inside `AppPreferences`, renders that preference in `ConfigModalFocusWorkspaceSection`, and loads preferences before restore in `AppShellState`.

Technical clarification chose a sub-toggle model: continuity should live under Focus Workspace rather than being folded into the existing boolean or becoming a separate top-level mode. The implementation must preserve the current non-opted-in workflow and avoid invalid preference combinations.

## Decision

Add a new `focusWorkspaceContinuityEnabled` boolean to `AppPreferences` and persist it in the existing app-preferences record.

The continuity toggle will be presented as a child option under Focus Workspace and must obey a parent-child invariant:

- if `focusWorkspaceEnabled` is `false`, `focusWorkspaceContinuityEnabled` must also be `false`
- continuity can only be active when Focus Workspace is active

The invariant will be enforced in core preference save or repair paths, not only in SwiftUI.

## Alternatives Considered

### Alternative 1: Reuse `focusWorkspaceEnabled` only

- **Description**: Extend the existing Focus Workspace toggle so continuity behavior is always implied when Focus Workspace is enabled.
- **Pros**: No new preference field, no schema change, simplest surface area.
- **Cons**: Couples two behaviors too tightly, makes rollout and experimentation less precise, and reduces room to keep existing Focus Workspace semantics stable while adding restore-first continuity.
- **Why rejected**: The user explicitly chose a sub-toggle so continuity can be opt-in within Focus Workspace.

### Alternative 2: Separate top-level mode

- **Description**: Create an independent continuity preference outside Focus Workspace.
- **Pros**: Clear isolation, easier future divergence if the product later renames or expands the feature.
- **Cons**: Adds product and technical surface area, weakens the current Focus Workspace mental model, and increases settings complexity for MVP.
- **Why rejected**: Too large for a restore-first MVP and inconsistent with the approved product approach.

## Consequences

### Positive

- Preserves the existing Focus Workspace contract while allowing continuity to evolve independently.
- Gives analytics and rollout a cleaner opt-in signal.
- Keeps the new behavior scoped to users who explicitly want it.

### Negative

- Requires a schema and preferences migration.
- Adds a new settings-state combination that must be validated and explained clearly.

### Risks

- Invalid persisted state could appear if the parent-child invariant is enforced only in UI.
- The settings surface could become confusing if the child toggle reads as a separate mode instead of an extension.

## Implementation Notes

- Extend `AppPreferences` with `focusWorkspaceContinuityEnabled` defaulting to `false`.
- Update `WorkspaceMigrations` and `SQLiteWorkspaceMetadataStore` to load and save the new field.
- Update `ConfigModalFocusWorkspaceSection` and `FocusWorkspacePresentation` to render the sub-toggle and clarify the dependency on Focus Workspace.
- Enforce and normalize the parent-child invariant in core preference save or load paths.
