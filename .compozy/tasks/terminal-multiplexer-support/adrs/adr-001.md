# ADR-001: Scope V1 as Focus Workspace continuity for multiplexer-heavy workflows

## Status

Accepted

## Date

2026-06-01

## Context

The original prompt was to improve usage with tmux, herdr, or any terminal multiplexer. Clarification narrowed the core pain to power-user developers who lose flow while switching panes or windows and want a minimal V1 that increases Focus Workspace adoption.

Repo research showed that Another ADE already has relevant foundations: a settings-first Focus Workspace policy, durable project/session/tab restore, keyboard-first switching, nested terminal-tab visibility, and launch-profile plumbing. The same research also showed hard limits: restore is metadata-only, there is no live pane model, no tmux/zellij integration, no true process reattach, and no remote or SSH continuity in scope.

Market research validated terminal-native and multiplexer-heavy workflows, but also showed a split between products that offer resume and parallel sessions versus smaller tools that go deeper on pane attention and continuity. The council agreed the product should not promise the second category of behavior unless it actually owns live external session state.

## Decision

V1 will extend Focus Workspace as a continuity layer for multiplexer-heavy workflows, not as true terminal-multiplexer integration.

The MVP should prioritize:

- opt-in Focus Workspace behavior aimed at tmux/herdr-style users
- fast return to the last meaningful work context inside the app
- stronger owned metadata for return-to-context flows such as last active project, session, tab, launch profile, and current working directory when available
- keyboard-first return-to-task behavior optimized for pane/window switching moments
- explicit product language that the experience is multiplexer-friendly while clearly avoiding any claim of live pane awareness or process reattachment

The primary success metric is Focus Workspace adoption among the target power-user cohort.

## Alternatives Considered

### Alternative 1: True tmux or multiplexer integration

- **Description**: Add live pane or window awareness, external session discovery, pane topology modeling, and process reattachment semantics.
- **Pros**: Stronger continuity story, sharper differentiation, closer parity with multiplexer-native tooling.
- **Cons**: Crosses product boundaries, creates adapter and support burden, requires live-state modeling the app does not own today, and risks misleading restore promises.
- **Why rejected**: Too large and structurally risky for a quick-win V1.

### Alternative 2: Copy-only extension of Focus Workspace

- **Description**: Keep the existing Focus Workspace behavior mostly unchanged and only improve framing, naming, or positioning for multiplexer-heavy users.
- **Pros**: Lowest implementation cost, fastest release path, preserves current architecture.
- **Cons**: Weak learning signal, limited user value, and unlikely to address the real pane/window switching pain strongly enough to move adoption.
- **Why rejected**: Too shallow to validate the opportunity credibly.

### Alternative 3: Rich continuity platform in V1

- **Description**: Introduce named workspace contexts, broader terminal-role metadata, and a larger working-set abstraction from the start.
- **Pros**: More coherent long-term model, clearer future extensibility, stronger continuity story.
- **Cons**: Adds schema, UI, migration, and support cost before evidence that users need the extra model complexity.
- **Why rejected**: Premature for the current learning goal, though some extensibility should be preserved.

## Consequences

### Positive

- Builds on current product strengths instead of inventing a new runtime boundary.
- Creates a credible multiplexer-friendly story without overpromising.
- Preserves a fast learning loop around adoption and return-to-context behavior.

### Negative

- Does not solve true live process continuity or external pane-state recovery.
- May feel incremental if the user's real need is deeper than rediscovery and focus recovery.
- Requires careful naming so the feature sounds valuable without sounding misleading.

### Risks

- The team could measure improved Focus Workspace usage without learning whether deeper continuity is the real unmet need.
- “Multiplexer support” wording could create false expectations if used as the primary frame.
- Ad hoc restore metadata could harden into accidental architecture unless the owned boundary is explicit.

## Implementation Notes

- Keep the V1 contract grounded in app-owned context recovery, not external terminal truth.
- Instrument the feature so the team can distinguish adoption gains from evidence that users actually need deeper continuity.
- Use multiplexer-friendly wording in supporting copy, but keep the primary product framing centered on Focus Workspace continuity.
- Leave live pane topology, remote or SSH continuity, tmux or zellij control, and process reattachment out of V1.
