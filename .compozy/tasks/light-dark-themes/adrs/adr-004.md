# ADR-004: Keep V1 Theme Expansion Inside the Existing Catalog and Generic Editor Mapping

## Status

Accepted

## Date

2026-05-31

## Context

Another ADE already applies theme state across several surfaces, but not all of them at the same fidelity. Shell chrome and terminal rendering use the full `AppTheme` palette and terminal appearance, while the file editor currently maps only to generic light or dark syntax themes through `@Environment(\.colorScheme)`.

The approved V1 scope prioritizes a disciplined release: add System support, expand the curated preset catalog, keep Settings simple, and improve perceived polish without turning the feature into a broad theming platform or a deep editor restyling project.

## Decision

Keep V1 theme expansion inside the existing `AppTheme` catalog and limit preset-aware runtime styling to shell and terminal surfaces. Preserve the current generic light/dark editor syntax mapping in V1.

Implementation rules:

- Add curated presets directly to `AppTheme.catalog`.
- Do not introduce a separate theme registry, plugin model, or external theme-definition files.
- Keep the Settings selector as a single ordered list composed of one synthetic System option followed by concrete presets.
- Continue using the current editor light/dark mapping based on resolved color scheme rather than adding preset-specific editor themes in V1.

## Alternatives Considered

### Alternative 1: Add a separate theme registry layer

- **Description**: Wrap concrete presets in a new registry abstraction and route Settings through that registry.
- **Pros**: Cleaner extension seam for future dynamic theme loading.
- **Cons**: More abstraction, more wiring, and more moving parts than V1 needs.
- **Why rejected**: The repo already has a functioning catalog seam, and YAGNI favors extending it directly.

### Alternative 2: Add preset-specific editor theme mapping in V1

- **Description**: Map each curated preset to a corresponding editor syntax theme and make editor styling match the shell more closely.
- **Pros**: Better visual fidelity across all surfaces.
- **Cons**: Increases scope, likely requires more compatibility work with the editor component, and adds more QA combinations.
- **Why rejected**: The user explicitly approved keeping editor theming at generic light/dark for V1.

## Consequences

### Positive

- Preserves the smallest-change architecture that fits the repo.
- Keeps theme additions local to `AppTheme.swift` and existing appearance UI.
- Avoids creating a new extensibility layer before there is proven demand.
- Limits V1 complexity while still improving visible appearance quality.

### Negative

- Full preset fidelity will not extend into editor syntax colors in V1.
- The product may still show minor visual mismatch between shell chrome and editor styling for some presets.
- Future dynamic theming work will still require a larger refactor if the scope later expands.

### Risks

- **Perceived consistency risk**: users may expect editor styling to match the selected preset more closely. Mitigation: ensure shell, overlays, and terminal are polished enough that the remaining mismatch is acceptable for V1.
- **Catalog maintenance risk**: adding too many presets directly to the catalog could make it harder to manage. Mitigation: keep the curated set short and stable.
- **Future extension risk**: later richer theming could outgrow the direct-catalog model. Mitigation: revisit only after V1 usage validates broader investment.

## Implementation Notes

- Keep preset definitions colocated with the current `AppTheme` catalog and helper types.
- Treat the Settings list ordering as part of the product contract for V1.
- Add tests for catalog ordering, System list behavior, and preset resolution without introducing editor-specific mapping logic.
