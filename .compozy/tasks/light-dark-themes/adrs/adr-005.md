# ADR-005: Centralize Effective Theme Resolution in the Theme Domain

## Status

Accepted

## Date

2026-05-31

## Context

Once `theme_id` can hold the reserved `system` selection, the app needs a consistent way to resolve that persisted selection into a concrete runtime `AppTheme`. Today, `WorkspaceStore.activeTheme` directly calls `AppTheme.resolve(id:)`, which only accepts concrete preset IDs and silently falls back to the default preset when the ID is unknown.

System mode also needs to react when macOS appearance changes while the app is running. That makes a purely persisted string lookup insufficient. The app needs one resolution seam that can combine persisted selection with current runtime light/dark state without scattering `system` checks throughout SwiftUI views and terminal-update code.

## Decision

Centralize effective theme resolution in the Theme domain by adding a shared `AppTheme` helper that accepts:

- the persisted appearance selection ID
- the current runtime scheme (`light` or `dark`)

The helper will return the concrete `AppTheme` that shell, editor, and terminal callers should use at runtime.

Implementation rules:

- `WorkspaceStore` continues to own persisted preferences, but it does not become responsible for observing or storing system appearance state.
- `ContentView` supplies the current runtime scheme from SwiftUI/macOS environment data into the shared resolver.
- Terminal updates, shell palette injection, and other runtime consumers must depend on the same resolved `AppTheme` value.

## Alternatives Considered

### Alternative 1: Resolve System inside `WorkspaceStore`

- **Description**: Make the store compute the effective concrete theme from persisted selection and runtime scheme.
- **Pros**: Keeps one observable source of truth close to current state ownership.
- **Cons**: Forces UI runtime concerns into the store and makes the store depend on information it does not naturally own.
- **Why rejected**: The store should remain persistence- and session-focused, not become a system-appearance observer.

### Alternative 2: Resolve System ad hoc inside `ContentView`

- **Description**: Keep System logic local to the root view without a shared helper.
- **Pros**: Smallest one-file change in the short term.
- **Cons**: Encourages duplicated logic, makes testing harder, and risks divergence between shell and terminal behavior.
- **Why rejected**: V1 still needs a testable, central resolution rule even if the overall scope stays small.

## Consequences

### Positive

- Creates one testable seam for concrete theme resolution.
- Keeps runtime system-appearance awareness out of persistence models and store ownership.
- Reduces the chance of shell and terminal drifting apart on System behavior.

### Negative

- Adds one more helper path to the theme domain.
- Requires `ContentView` and related runtime consumers to switch from simple preset lookup to explicit effective-theme resolution.

### Risks

- **Boundary drift risk**: the helper could grow beyond resolution into a broader runtime theming service. Mitigation: keep it limited to pure selection-to-theme mapping.
- **Update propagation risk**: callers may accidentally keep using direct `AppTheme.resolve(id:)` instead of the shared resolver. Mitigation: update the spec and tests to make the effective resolver the single runtime path for appearance selection.

## Implementation Notes

- Keep the helper pure and deterministic so unit tests can cover selection ID + runtime scheme combinations.
- Preserve `AppTheme.resolve(id:)` for concrete preset lookup, but route all runtime appearance selection through the new effective resolver.
