# ADR-003: Persist System Appearance as a Reserved Theme Selection

## Status

Accepted

## Date

2026-05-31

## Context

Another ADE already persists appearance in `app_preferences.theme_id` and derives the active theme from that single value. The current runtime assumes that every stored ID resolves directly to a concrete `AppTheme` entry, and `ContentView` forces a fixed `preferredColorScheme` from the resolved theme.

V1 now needs a System option that follows the current macOS appearance while staying compatible with the existing startup, persistence, validation, and restore flow. The design should stay additive and avoid a broader preferences model unless there is clear V1 value.

## Decision

Persist System appearance as a reserved `theme_id` value, `system`, inside the existing `app_preferences` row.

Implementation rules:

- `AppTheme` remains the catalog of concrete presets only.
- `system` is handled as a selection state, not as a concrete theme preset.
- New installs and missing-preference fallback paths seed `theme_id` to `system`.
- When `theme_id == system`, runtime resolution picks the first light preset when macOS is in light appearance and the first dark preset when macOS is in dark appearance.
- Validation logic must accept `system` alongside concrete preset IDs.
- When selection is `system`, the app must stop forcing a fixed `preferredColorScheme` and instead follow the OS appearance while still resolving shell and terminal visuals from the chosen concrete preset.

## Alternatives Considered

### Alternative 1: Persist separate light and dark preset IDs for System

- **Description**: Add explicit stored values for a system light preset and a system dark preset.
- **Pros**: More flexible and future-proof if System later becomes user-configurable.
- **Cons**: Requires more persistence changes, more validation logic, and a larger configuration surface than V1 needs.
- **Why rejected**: V1 does not need user-configurable System mapping, and the added model complexity would exceed the approved scope.

### Alternative 2: Treat System as a temporary UI-only mode

- **Description**: Keep persistence limited to concrete preset IDs and derive System only in UI state.
- **Pros**: Avoids expanding persistence validation.
- **Cons**: Breaks predictability across relaunches and weakens the existing single-source-of-truth model.
- **Why rejected**: The PRD requires reliable appearance memory, and transient UI-only state would violate that expectation.

## Consequences

### Positive

- Keeps the change inside the existing `AppPreferences.themeID` seam.
- Avoids new tables or preference columns in V1.
- Preserves a single persisted source of truth for appearance selection.
- Makes fresh installs align with the PRD's System-first product behavior without extra onboarding logic.
- Leaves room for future configurable System mapping if usage later justifies it.

### Negative

- System behavior becomes dependent on catalog ordering for the first light and first dark presets.
- Validation and runtime resolution must treat `system` differently from ordinary preset IDs.
- The editor still receives only generic light/dark behavior rather than a truly System-specific style contract.
- Existing installations that already have a concrete theme ID will keep that value until the user changes it.

### Risks

- **Catalog-order risk**: changing preset order later could silently change System behavior. Mitigation: document and test the first-light/first-dark contract.
- **Runtime resolution risk**: System must react correctly to OS appearance changes without breaking terminal or shell updates. Mitigation: keep one resolver and cover it with integration tests.
- **User expectation risk**: users may assume they can configure which presets System uses. Mitigation: keep the Settings language clear and defer configurable pairing to future scope.
- **Repair-path risk**: stale or invalid theme IDs now recover to `system` instead of a fixed preset. Mitigation: update tests and user-visible expectations around fallback behavior.

## Implementation Notes

- Keep the reserved `system` handling close to the theme resolution boundary rather than scattering special cases through the UI.
- Update unknown-theme repair logic so `system` is treated as valid.
- Update default seeding so fresh `AppPreferences` rows start at `system`.
- Add tests for relaunch behavior, runtime switching, and first-light/first-dark resolution.
