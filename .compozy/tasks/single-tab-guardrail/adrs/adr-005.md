# ADR-005: Persist Focus Workspace as an app-global preference in AppPreferences with a v6 migration

## Status

Accepted

## Date

2026-06-01

## Context

The PRD defines Focus Workspace as an optional user preference, not a per-project or per-session policy. The existing codebase already models app-global settings in `AppPreferences`, stores them in the single-row `app_preferences` table, loads them during startup before restore, and updates them through `saveAppPreferences(_:)`.

Because the feature must survive relaunch and shape future tab-creation behavior, the implementation needs a durable preference in the current app-preferences pipeline rather than ephemeral UI state.

## Decision

Add an app-global boolean preference to `AppPreferences` and persist it in `app_preferences` through a new SQLite metadata migration.

The implementation will:

- add `focusWorkspaceEnabled` to `AppPreferences` with a default value of `false`
- extend the `app_preferences` schema with a non-null boolean column through migration v6
- load and save the new field through `SQLiteWorkspaceMetadataStore`
- keep the feature app-global and avoid any session- or tab-level persistence flags

## Alternatives Considered

### Alternative 1: Persist the feature on each session

- **Description**: Store Focus Workspace state on sessions so some sessions opt in and others do not.
- **Pros**: More granular control and fewer global trade-offs.
- **Cons**: Directly conflicts with the approved product scope, complicates restore and selection behavior, and expands the feature into policy management.
- **Why rejected**: The PRD explicitly keeps the feature app-level and personal, not per-session.

### Alternative 2: Keep the feature as non-persisted UI state

- **Description**: Hold the mode only in SwiftUI shell state and reset it on relaunch.
- **Pros**: No migration work and no persistence changes.
- **Cons**: Breaks the PRD requirement for trustworthy resume behavior and makes the feature feel transient or buggy.
- **Why rejected**: The feature must be understandable after relaunch and must shape future commands consistently.

## Consequences

### Positive

- Reuses the existing settings lifecycle with minimal new architectural surface.
- Keeps ownership aligned with current settings save/load logic.
- Lets startup know the preference state before restore and shell composition decisions.

### Negative

- Requires a schema migration and metadata repair path.
- Expands the single-row app-preferences payload, so query and save code must stay in sync.

### Risks

- A partial migration or missing default could cause startup preference load failures.
- If future scope later wants per-session focus behavior, the app-global field will need redesign rather than extension.

## Implementation Notes

- Bump `WorkspaceMigrations.currentUserVersion` from 5 to 6.
- Add the new column with a default of `0` / false and include it in bootstrap inserts, query decoding, and save upserts.
- Keep startup ordering unchanged: load preferences first, then restore.
