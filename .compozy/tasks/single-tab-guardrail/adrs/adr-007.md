# ADR-007: Use a shared pure Focus Workspace policy helper instead of duplicating rules in views and commands

## Status

Accepted

## Date

2026-06-01

## Context

Focus Workspace needs the same rule set in two places: `DefaultWorkspaceCommandService` must enforce the policy as the mutation boundary, and SwiftUI surfaces must hide or show affordances consistently with that policy. If each view computes its own tab-count and exception logic separately, the feature will drift. At the same time, the feature is too small to justify a new service layer or a full policy subsystem.

The chosen technical approach needs a small, reusable definition of session compliance and allowed actions that both command logic and UI affordances can reference without adding a new package hierarchy.

## Decision

Introduce a small shared pure policy helper in `NativeMacADECore` to evaluate Focus Workspace state and allowed actions.

The helper will:

- derive session compliance from `AppPreferences` plus the current session’s visible terminal/file tabs
- expose read-only decisions such as whether a terminal tab can be created, whether a file open is allowed, and whether the tab row can be hidden
- stay side-effect free so command code remains the only mutation owner
- be reusable by both `DefaultWorkspaceCommandService` and SwiftUI affordance logic

## Alternatives Considered

### Alternative 1: Duplicate small rules in each view and command path

- **Description**: Let menus, tab chrome, file sidebar, and command service each compute their own focus checks.
- **Pros**: No new shared type and minimal up-front refactoring.
- **Cons**: High drift risk, harder testing, and inconsistent hide/block behavior over time.
- **Why rejected**: The feature already touches many entry points, and duplicated policy would become the main maintenance risk.

### Alternative 2: Add a dedicated Focus Workspace service or subsystem

- **Description**: Build a new stateful service that owns focus-mode decisions for the whole app.
- **Pros**: Strong central ownership and room for future expansion.
- **Cons**: Too much abstraction and surface area for an MVP feature, especially when the current architecture already has a command service and observable store.
- **Why rejected**: Over-engineered for the current scope.

## Consequences

### Positive

- Keeps the rule set testable in isolation.
- Reduces drift between UI affordances and command enforcement.
- Preserves the existing ownership model: pure helper for decisions, command service for mutations.

### Negative

- Adds one new shared type to the core layer.
- Requires discipline so the helper does not grow into a larger pseudo-service.

### Risks

- If the helper starts absorbing mutation behavior, the command boundary will erode.
- If views bypass the helper and recompute logic anyway, the abstraction loses value.

## Implementation Notes

- Keep the helper in an existing core package, likely alongside workspace or command logic.
- Prefer a tiny struct/enum plus pure functions over protocols or stateful objects.
- Limit the helper to evaluation of current session state and action eligibility.
