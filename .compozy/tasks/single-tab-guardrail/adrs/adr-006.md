# ADR-006: Allow one terminal tab plus one optional file tab and hide blocked terminal-tab affordances

## Status

Accepted

## Date

2026-06-01

## Context

The original idea described a one-tab experience, but the approved technical clarifications introduced a file-oriented exception. When Focus Workspace is active, opening a file from the sidebar or search should still be able to create a file tab even if a terminal surface is already visible. At the same time, the user chose to allow only one file tab per session, to hide blocked terminal-tab affordances where possible, and to reuse the existing shell alert pattern for blocked attempts.

That means the feature needs a precise allowed-state matrix and UI strategy that preserves a coherent user model without turning Focus Workspace into a full tab-management system.

## Decision

Model Focus Workspace as allowing at most one terminal tab and one optional file tab per session.

The implementation will:

- allow the existing or newly created terminal surface to remain the primary focused surface
- allow creation of a first file tab while Focus Workspace is active
- allow same-file reopen to reuse the existing file tab
- block opening a different file once a file tab already exists in that session
- hide terminal-tab creation affordances where the shell can determine they would be blocked
- keep the tab row visible whenever the selected session has more than one visible tab, even if Focus Workspace is enabled
- map blocked attempts to friendly `UserMessage` alerts through a dedicated command error

## Alternatives Considered

### Alternative 1: Strict single-surface mode with no file-tab exception

- **Description**: Enforce exactly one visible tab with no file exception while Focus Workspace is active.
- **Pros**: Simplest invariant and easiest explanation.
- **Cons**: Conflicts with the approved file-opening behavior and makes file inspection too restrictive for the selected workflow.
- **Why rejected**: The user explicitly chose to allow a file-tab exception.

### Alternative 2: Reusable single file slot for any file

- **Description**: Keep one file tab but repurpose it automatically whenever a different file is opened.
- **Pros**: Preserves the one-file-tab limit while keeping file navigation flexible.
- **Cons**: More surprising behavior, greater risk of accidental context replacement, and extra state-management complexity in MVP.
- **Why rejected**: The selected direction did not approve replacement semantics, and blocking later different-file opens is the lower-risk MVP path.

### Alternative 3: Keep commands visible and fail on use

- **Description**: Leave terminal-tab commands fully visible and explain the restriction only after users trigger them.
- **Pros**: Lower UI churn and fewer view changes.
- **Cons**: Makes the mode feel noisy and punitive, and undermines the PRD’s in-product clarity goals.
- **Why rejected**: The approved clarification explicitly prefers hiding blocked affordances where possible.

## Consequences

### Positive

- Preserves a focused terminal workflow while still supporting limited file inspection.
- Keeps the MVP state matrix small enough to reason about and test.
- Reduces unnecessary blocked actions by hiding known-disallowed terminal-tab affordances.

### Negative

- Focus Workspace is no longer a literal one-tab invariant.
- The tab row cannot always disappear while the feature is active.
- Different-file opens after the first file tab can still produce blocking friction.

### Risks

- Users may misunderstand the feature if naming and UI imply a stricter invariant than the implementation actually enforces.
- If hidden affordances and command-layer rules diverge, the product will feel inconsistent.
- Existing generic error rendering can make blocked attempts feel too technical unless mapped carefully.

## Implementation Notes

- Derive the allowed-state matrix from the selected session’s visible tabs rather than from persisted legacy metadata.
- Gate `createTab`, `createPlainTab`, `createDefaultAgentTab`, and `createAgentTab` when the session already has a terminal tab under Focus Workspace.
- Gate `openFileTab` so same-file reopen selects the existing file tab, the first file tab can be created, and later different-file opens are rejected while a file tab exists.
- Hide or suppress tab-creation buttons and menu items that can be statically known to be disallowed, but rely on the command-service error as the source of truth.
