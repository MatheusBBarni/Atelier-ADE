# ADR-004: Enforce Focus Workspace at the command layer and grandfather existing multi-tab sessions

## Status

Accepted

## Date

2026-06-01

## Context

Single-Tab Guardrail evolved into a broader Focus Workspace feature, but the relevant user-visible actions are still spread across multiple surfaces: app menus, keyboard shortcuts, the tab bar, empty states, the agent palette, and file-opening flows. The existing architecture already centralizes durable workspace mutations in `WorkspaceCommandService` and `DefaultWorkspaceCommandService`, while SwiftUI views mostly route user intent into those commands.

The approved technical direction is future-only enforcement. When a user enables Focus Workspace while existing sessions already contain multiple tabs, the implementation should not auto-collapse or block enablement. Restore should stay preference-agnostic at the metadata layer, and compliance should be enforced only on future create/open commands.

## Decision

Implement Focus Workspace as a command-layer policy enforced in `DefaultWorkspaceCommandService`, not as a view-owned rule and not as a restore-time normalization pass.

The implementation will:

- centralize Focus Workspace gating in command paths that create or open additional surfaces
- keep `RestoreCoordinator` preference-agnostic and policy-free
- grandfather existing non-compliant sessions instead of mutating them on enablement or restore
- derive compliance from the current visible session state rather than storing legacy-exemption metadata
- use a dedicated `WorkspaceCommandError` case for focus-policy rejections so UI surfaces can map the failure consistently

## Alternatives Considered

### Alternative 1: View-layer gating only

- **Description**: Hide or disable tab-creation controls in SwiftUI, but leave command behavior unchanged.
- **Pros**: Fastest visible change, lowest short-term code movement in the core layer.
- **Cons**: Leaves keyboard shortcuts, restore, and other entry points inconsistent; correctness depends on every view remembering the rule.
- **Why rejected**: The codebase already has a command-service boundary for durable workspace mutations, and view-only enforcement would drift quickly.

### Alternative 2: Normalize sessions on enablement or restore

- **Description**: Collapse or reconcile existing multi-tab sessions as soon as Focus Workspace turns on or during restore.
- **Pros**: Produces a cleaner invariant after enablement and makes the feature easier to describe.
- **Cons**: Surprising state mutation, more restore coupling, more user-risk around file tabs and dirty buffers, and directly rejected by the chosen future-only policy.
- **Why rejected**: The approved behavior is future-only, and forced normalization adds unnecessary product and restore complexity.

## Consequences

### Positive

- Keeps correctness at the existing mutation boundary.
- Avoids surprising retroactive changes to current user sessions.
- Preserves a simpler restore layer with fewer hidden feature flags.
- Makes terminal-tab, agent-tab, and file-tab rules testable in one place.

### Negative

- Existing multi-tab sessions can remain visible while Focus Workspace is enabled.
- The feature cannot be described as a literal global single-tab invariant.
- Some UI affordances must derive state from session compliance rather than a simple feature flag alone.

### Risks

- If any create/open path bypasses the command service, Focus Workspace will leak.
- If UI copy suggests a strict one-tab rule, grandfathered legacy sessions may confuse users.
- If restore-side code starts applying focus policy independently later, the system can drift into split ownership.

## Implementation Notes

- Keep the policy as a small helper inside the existing command-service implementation rather than introducing a new service layer.
- Apply focus checks in terminal-tab creation and file-opening flows only; do not expand the feature into reorder, rename, or navigation logic.
- Preserve legacy sessions unchanged, but ensure future blocked attempts report a dedicated focus-policy error.
