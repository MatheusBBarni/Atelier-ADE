# ADR-001: Scope V1 as a settings-first single-tab preference with real enforcement

## Status

Accepted

## Date

2026-05-31

## Context

Another ADE is evaluating a feature idea for focused solo users who want a simpler workspace: hide the tab row and prevent creation of additional tabs so each session effectively behaves as a single-tab session. The user problem is twofold: reduce visible UI clutter and reduce wrong-tab mistakes for people who usually work in one thread at a time.

Research across VS Code, IntelliJ IDEA, Windows Terminal, and similar tools shows clear demand for optional focus or distraction-reduction modes, but most of those products simplify the UI more than they enforce behavior. Research on tab overload also shows real discoverability, stress, and attention costs when users accumulate too many tabs.

Within Another ADE, the idea is more coupled than it first appears. Sessions and tabs are different concepts, file tabs and terminal tabs share one tab namespace, tab creation has several entry points, and restore can reopen prior tab state. That means a cosmetic “hide tabs” toggle would create invisible state and a misleading mental model unless the behavior is enforced below the UI.

## Decision

Ship V1 as a narrow, opt-in preference in the existing Settings surface that enforces single-tab behavior per session end to end.

The accepted V1 scope will:

- add one clearly named personal-preference setting in the existing config modal
- hide the main tab row when the preference is enabled and the session is operating in single-tab mode
- enforce the single-tab rule at the command layer across all tab-creation paths, not only in visible UI controls
- define explicit restore behavior so enabling the preference does not silently resurrect hidden extra tabs
- keep product framing narrow: this is a personal-preference simplification feature, not a broad new “single-session mode” platform

The accepted V1 will not depend on a new onboarding flow. If setup-time discoverability matters later, it can be layered on after the preference proves value.

## Alternatives Considered

### Alternative 1: Cosmetic hide-tabs toggle only

- **Description**: Add a settings flag that hides the tab row and maybe removes the plus button, but do not enforce behavior in commands or restore.
- **Pros**: Fastest UI implementation, low visible scope, easy to demo.
- **Cons**: Creates invisible multi-tab state, leaks through non-UI tab creation paths, and undermines trust when restore or commands reopen tabs users cannot see.
- **Why rejected**: The feature promise is simplicity and fewer tab mistakes. A visual-only toggle would likely make both worse.

### Alternative 2: Broader single-session or focus-mode platform in V1

- **Description**: Turn this into a larger workspace mode with onboarding/setup choices, stronger mode signaling, and potentially more session-level behavioral changes.
- **Pros**: Stronger positioning, clearer identity, and a more ambitious product story.
- **Cons**: Expands scope into onboarding, mode semantics, copy, recovery behavior, and broader workflow design before demand is validated.
- **Why rejected**: Too large for the current learning goal and not necessary to test the core user value hypothesis.

### Alternative 3: Defer until broader session/tab clarity work is complete

- **Description**: Prioritize general wrong-tab visibility and navigation improvements first, then revisit this preference later.
- **Pros**: Improves a broader user problem and reduces the chance of building around a narrow persona too early.
- **Cons**: Delays learning on whether a focused single-tab preference is independently valuable, and leaves a known simplicity preference unmet.
- **Why rejected**: Reasonable fallback if enforcement cost proves too high, but not the preferred path if command-layer and restore guardrails are affordable.

## Consequences

### Positive

- Preserves a small, testable scope tied to an identifiable user segment.
- Aligns the feature with existing Settings patterns instead of inventing a new product surface.
- Keeps the user promise truthful by requiring behavioral enforcement rather than visual hiding alone.
- Creates measurable learning around adoption, retention, and wrong-tab reduction.

### Negative

- Reach is limited because the feature is optional and persona-specific.
- The feature will not materially help users who prefer multi-tab workflows.
- Enforcement and restore rules make the work larger than the UI description suggests.

### Risks

- File-tab behavior may be contentious because file and terminal tabs share one tab model.
- Restore policy may surprise users if older multi-tab sessions must be collapsed, blocked, or otherwise reconciled.
- Silent rerouting of “open new tab” actions could create long-term ambiguity unless those paths are explicitly defined as singleton-safe.
- The feature could be mistaken for a broader workflow mode if naming and copy are imprecise.

## Implementation Notes

- Treat the invariant as behavioral: when enabled, second-tab creation should not succeed unless the action is explicitly modeled as safe singleton reuse.
- Prefer blocking over implicit rerouting unless a command already has clear “open-or-focus current surface” semantics.
- Define enable-time behavior for existing multi-tab sessions and define restore semantics before UI polish.
- Keep onboarding, per-project policy, and broader workspace-mode expansion out of V1.
