# ADR-003: Broaden MVP through in-product framing before public positioning

## Status

Accepted

## Date

2026-05-31

## Context

After selecting the broader focus-workspace product approach for the PRD, the next scope decision was where that broader expression should show up first. The approved idea had included README and website positioning for terminal-multiplexer-friendly workflows, but PRD clarification answers did not support expanding the MVP publicly first. Repo context also showed that current public messaging still emphasizes sessions, tabs, and restore, while the product already has an in-app settings surface and multiple user-facing tab-entry points that need clearer focus-oriented framing.

The user chose to broaden the MVP first through in-product framing rather than public positioning. That means the PRD should prioritize discoverability, clarity, and user guidance inside Atelier itself before turning the feature into a larger external marketing story.

## Decision

The MVP will broaden the single-tab guardrail through in-product framing first.

This means the PRD should prioritize:

- stronger in-app discoverability and mode clarity
- clearer user-facing explanation of what the focus-oriented experience does and does not do
- a more deliberate in-product experience when the preference is active

Public positioning through README and website messaging may follow in a later phase if the MVP proves valuable.

## Alternatives Considered

### Alternative 1: Public positioning first

- **Description**: Expand README and website messaging in MVP so the feature becomes part of Atelier’s external product story immediately.
- **Pros**: Stronger positioning, clearer acquisition story, better support for switchers evaluating the product.
- **Cons**: Raises the public promise before the in-product experience is fully validated and polished.
- **Why rejected**: The user chose to prioritize the in-product experience before broader outward-facing storytelling.

### Alternative 2: Broaden both in-product framing and public positioning together

- **Description**: Use MVP to expand both the in-app experience and the external messaging in one release.
- **Pros**: Most coherent overall story, fastest path to a larger market-facing narrative.
- **Cons**: Adds coordination and scope before the product value is proven with users.
- **Why rejected**: Too expansive for the approved direction and weakens YAGNI discipline.

## Consequences

### Positive

- Keeps the MVP grounded in user experience rather than messaging alone.
- Lets the product validate the feature where current users will actually feel it.
- Preserves a cleaner Phase 2 story if public positioning follows evidence.

### Negative

- External discoverability and acquisition benefits will likely come later.
- The feature may remain under-signaled to prospective users until a follow-up phase.

### Risks

- If in-product framing is too subtle, the broader approach may still feel like a narrow toggle.
- If public messaging waits too long, the feature may not contribute meaningfully to product differentiation in the near term.

## Implementation Notes

- The PRD should include in-product discoverability and clarity as part of MVP scope.
- README and website updates should be described as later-phase opportunities unless the draft review changes this decision.
