# ADR-007: Validate Ghostty migration with manual baseline QA and focused runtime unit tests

## Status

Accepted

## Date

2026-06-02

## Context

The PRD defines a correctness baseline across interactive TUIs, shell behavior, rendering fidelity, and heavy output, with any regression versus current Atelier terminal behavior treated as a failure. Technical clarification selected a validation mix: manual QA checklist coverage for terminal correctness plus focused unit tests around `CGhosttyRuntime` and launch configuration.

Full automated parity testing against standalone Ghostty would be expensive and brittle for the MVP. Unit-only testing would miss the visible terminal behavior users care about.

## Decision

The TechSpec will require two validation layers:

- focused automated tests for Ghostty runtime wrapping, launch metadata translation, host lifecycle, errors, close checks, focus, resize, and exit events
- a manual QA checklist for the baseline workflows: interactive TUIs, shell behavior, rendering fidelity, and heavy output

The MVP will not require snapshot-render parity tests against standalone Ghostty.

## Alternatives Considered

### Alternative 1: Automated adapter and scripted baseline checks

- **Description**: Add automated host integration tests plus scripted command-line checks for all baseline workflow classes.
- **Pros**: Better regression automation.
- **Cons**: Hard to make reliable for native terminal UI behavior and may overbuild MVP validation.
- **Why rejected**: Manual baseline QA plus focused unit tests is more pragmatic for the first Ghostty migration.

### Alternative 2: Snapshot-render tests against standalone Ghostty

- **Description**: Compare Atelier terminal rendering against standalone Ghostty output.
- **Pros**: Strong parity signal.
- **Cons**: Brittle, expensive, and outside the PRD's non-goal of full standalone Ghostty parity.
- **Why rejected**: The MVP targets no regression versus current Atelier behavior, not exhaustive standalone parity.

### Alternative 3: Unit tests only around CGhosttyRuntime and launch configuration

- **Description**: Limit automated validation to runtime and launch types.
- **Pros**: Fast and stable.
- **Cons**: Misses the visible terminal behavior baseline.
- **Why rejected**: Manual QA is still required to validate user-facing terminal correctness.

## Consequences

### Positive

- Keeps automated tests focused and maintainable.
- Ensures visible terminal behavior is checked before release.
- Avoids brittle Ghostty parity snapshots.

### Negative

- Some correctness validation remains manual.
- Manual checklist quality depends on representative workflow examples.

### Risks

- Manual QA could miss regressions without clear checklist steps.
- Future changes may regress terminal behavior unless the automated layer grows over time.

## Implementation Notes

- Keep the checklist in the TechSpec or follow-on task artifacts.
- Add automated coverage around non-visual contracts: launch metadata, surface creation, close checks, focus, resize, exit events, and failure mapping.
- Convert SwiftTerm-specific tests into Ghostty-host or launch-translation tests.
