# ADR-003: Replace the SwiftTerm terminal path inside TerminalHostController with Ghostty surfaces

## Status

Accepted

## Date

2026-06-02

## Context

The PRD requires every Atelier terminal tab to use Ghostty while preserving the current project, session, tab, restore, and agent launch workflow. The codebase already has a stable workspace-facing seam: `DefaultWorkspaceCommandService` depends on `WorkspaceTerminalSurfaceManaging`, and `TerminalHostController` implements that protocol.

The current live `TerminalHostController` path still routes through `TerminalSessionDriver` and `SwiftTerm.LocalProcessTerminalView` because `LiveGhosttyAdapter.usesEmbeddedSessionDriver` returns `true`. This means the Ghostty-named adapter exists, but the user-visible terminal is still SwiftTerm-backed.

## Decision

The implementation will keep `WorkspaceTerminalSurfaceManaging` and `DefaultWorkspaceCommandService` stable, then replace the SwiftTerm session-driver branch inside `TerminalHostController` with real Ghostty-backed surfaces.

`TerminalHostController` remains responsible for tab-to-surface identity, host view attachment, focus, resize, close checks, exit monitoring, release, and appearance updates. The Ghostty adapter/runtime boundary becomes responsible for creating and controlling the actual terminal surface.

## Alternatives Considered

### Alternative 1: Add a new terminal-engine abstraction above TerminalHostController

- **Description**: Introduce a new runtime abstraction above `TerminalHostController`, then implement Ghostty behind it.
- **Pros**: More explicit engine layering and potential future support for multiple terminal engines.
- **Cons**: Adds indirection before the product needs it and risks touching broader app contracts.
- **Why rejected**: The MVP explicitly does not expose terminal-engine choice. The current protocol seam is sufficient.

### Alternative 2: Keep SwiftTerm as a selectable runtime path

- **Description**: Preserve the current SwiftTerm path and add Ghostty as an alternate runtime.
- **Pros**: Provides fallback during migration.
- **Cons**: Keeps two production terminal runtimes and weakens the product requirement that Ghostty is the terminal.
- **Why rejected**: The MVP should replace the current terminal path, not add a hidden engine selector.

## Consequences

### Positive

- Preserves existing workspace contracts.
- Concentrates the migration in the terminal-host and Ghostty runtime layers.
- Gives the product a clear default Ghostty terminal path.

### Negative

- Existing SwiftTerm-specific tests must be rewritten or removed.
- `TerminalHostController` must correctly host the native Ghostty view instead of a SwiftTerm view.
- The adapter boundary must expose enough lifecycle behavior for close and exit semantics.

### Risks

- Focus, resize, and exit behavior may regress if the Ghostty native view lifecycle differs from the current SwiftTerm view.
- AppKit host attachment bugs could break restored or reused tab views.

## Implementation Notes

- Keep `DefaultWorkspaceCommandService` and persisted workspace models unchanged.
- Remove the `usesEmbeddedSessionDriver` branch once Ghostty surface hosting is complete.
- Preserve existing telemetry names such as `terminal_surface_failed` and `terminal_process_exited`.
