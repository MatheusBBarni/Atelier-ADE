# ADR-001: Use Ghostty as the Atelier terminal while preserving the Atelier workflow

## Status

Accepted

## Date

2026-06-02

## Context

The requested product change is to use Ghostty instead of the current embedded terminal experience. Clarification narrowed the desired outcome to a cmux-like terminal foundation: Atelier should use Ghostty as its terminal, but the MVP should not redesign Atelier around cmux-style panes, splits, or agent attention features.

Repo research showed that Atelier already has a Ghostty-named boundary through `ThirdParty/Ghostty`, `CGhostty`, `GhosttyAdapter`, and `GhosttyLaunchConfiguration`. The same research showed that live terminal tabs still route through the current embedded local terminal session driver. The product need is therefore not naming or placeholder metadata. The product need is for users to experience Ghostty-level terminal correctness inside existing Atelier tabs.

Market research showed that power users compare terminal quality through correctness, native behavior, rendering fidelity, and confidence under real command-line workflows. Ghostty and cmux both reinforce the expectation that a native macOS tool can offer a high-quality terminal foundation without forcing users to leave the app.

## Decision

The MVP will make every Atelier terminal tab use Ghostty as the terminal experience while preserving the current Atelier project, session, tab, restore, and agent launch workflow.

The MVP should prioritize:

- terminal correctness for power users who expect Ghostty-level behavior
- current Atelier terminal-tab workflows remaining familiar
- Ghostty use being the default terminal experience, not an optional experiment
- honest product scope that does not promise Ghostty config parity, pane workflows, or cmux-style agent attention in the first release

## Alternatives Considered

### Alternative 1: Ghostty terminal plus config parity

- **Description**: Use Ghostty and also promise familiar Ghostty configuration behavior for fonts, themes, and key behavior in the MVP.
- **Pros**: Stronger parity signal for Ghostty users and clearer connection to standalone Ghostty expectations.
- **Cons**: Broadens MVP scope beyond the core terminal replacement and creates a larger compatibility promise.
- **Why rejected**: The first release should prove that Atelier uses Ghostty as the terminal experience before expanding the configuration surface.

### Alternative 2: Ghostty terminal plus cmux-style workflow

- **Description**: Use Ghostty and add panes, splits, agent attention signals, or other cmux-style workflow features.
- **Pros**: Stronger competitive comparison against cmux and a more visible product change.
- **Cons**: Mixes terminal replacement with workflow redesign and overlaps existing multiplexer-continuity work.
- **Why rejected**: Too broad for the MVP and likely to distract from validating Ghostty as the terminal foundation.

### Alternative 3: User-selectable terminal engines

- **Description**: Let users choose between the current terminal and Ghostty-backed terminal tabs.
- **Pros**: Gives users a fallback and reduces migration anxiety.
- **Cons**: Creates two terminal experiences to support and weakens the product statement that Ghostty is the new terminal.
- **Why rejected**: The requested outcome is to use Ghostty as Atelier's terminal, not to add another preference.

## Consequences

### Positive

- Gives the feature a crisp user-visible promise.
- Keeps the MVP focused on terminal quality instead of broader workflow redesign.
- Builds on existing Ghostty-related repository boundaries without letting placeholder naming define success.

### Negative

- Users who expect Ghostty configuration parity may need to wait for later phases.
- Users comparing directly with cmux panes or agent attention features will not see those workflows in the MVP.
- The product must clearly distinguish "uses Ghostty as the terminal" from "matches every standalone Ghostty feature."

### Risks

- Power users may judge the MVP harshly if common terminal behavior still differs from Ghostty.
- Existing terminal sessions could feel disrupted if the migration changes familiar app-level workflows.
- The Ghostty comparison could invite expectations outside the MVP unless release messaging is precise.

## Implementation Notes

- Preserve current Atelier workflow semantics: projects, sessions, tabs, restore, and agent launch profiles.
- Treat Ghostty as the default terminal experience for terminal tabs.
- Keep config parity, panes, splits, and cmux-style agent attention out of the MVP unless a later PRD expands scope.
