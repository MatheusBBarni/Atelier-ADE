# ADR-006: Preserve existing launch metadata and translate it into Ghostty launch configuration

## Status

Accepted

## Date

2026-06-02

## Context

Atelier stores terminal launch behavior in `WorkspaceTab` through working directory, shortcut ID, launch command, and launch arguments JSON. Session creation, agent tabs, restore, and tests depend on that metadata. The PRD requires existing project, session, tab, restore, and agent launch flows to remain unchanged.

The current SwiftTerm path adds shell and agent-specific launch behavior inside `TerminalSessionDriver`, including command-line construction and environment overrides. The Ghostty migration must preserve the user-facing behavior without tying it to SwiftTerm.

## Decision

The implementation will preserve existing persisted launch metadata and translate it into Ghostty launch configuration.

No workspace metadata schema change is required. Existing terminal tabs remain terminal tabs, and Ghostty becomes the runtime behind them. Launch translation should preserve working directory, plain shell starts, stored launch command, launch arguments, and current agent-specific launch behavior.

## Alternatives Considered

### Alternative 1: Redesign launch commands around Ghostty config files

- **Description**: Move launch behavior into Ghostty configuration semantics.
- **Pros**: Aligns with standalone Ghostty concepts.
- **Cons**: Expands MVP scope into config parity and changes app-owned launch semantics.
- **Why rejected**: The PRD explicitly preserves Atelier workflows and defers config parity.

### Alternative 2: Preserve only plain shell sessions for MVP

- **Description**: Implement Ghostty for normal shells first and defer agent launch compatibility.
- **Pros**: Smaller technical surface.
- **Cons**: Breaks a core Atelier workflow and violates the non-regression baseline.
- **Why rejected**: Agent launch flows must remain unchanged for the MVP.

### Alternative 3: Add a terminal engine marker to persisted metadata

- **Description**: Store a terminal-engine field on restored tabs.
- **Pros**: Could support future multi-engine migration.
- **Cons**: Unneeded for a single Ghostty runtime and introduces schema churn.
- **Why rejected**: Existing terminal tabs can remain runtime-agnostic.

## Consequences

### Positive

- Avoids persistence migration.
- Preserves existing restore and agent-tab behavior.
- Keeps launch behavior testable outside the native view layer.

### Negative

- Launch-command translation must be lifted out of SwiftTerm-specific code.
- Some current behavior may need explicit mapping into Ghostty launch APIs.

### Risks

- Agent-specific environment behavior could regress if translation omits current overrides.
- Shell alias and interactive login behavior may differ when launched by Ghostty unless explicitly validated.

## Implementation Notes

- Extract launch translation into a testable Swift type independent of `TerminalSessionDriver`.
- Keep existing command escaping and agent-specific argument/environment behavior covered by tests.
- Reuse `GhosttyLaunchConfiguration` as the core Swift launch payload unless the wrapper target needs a narrower native payload.
