# ADR-005: Add a Swift-native Ghostty wrapper target and keep CGhostty as native interop scaffolding

## Status

Accepted

## Date

2026-06-02

## Context

The repository already has a `CGhostty` C target that exposes a tiny app-owned ABI and a `CGhosttyRuntime` Swift wrapper. `ThirdParty/Ghostty/GhosttyPin.json` notes that `CGhostty` currently acts as a boundary for a pinned libghostty revision. The technical clarification selected a different boundary shape for the real integration: add a Swift-native wrapper target while leaving `CGhostty` as compatibility scaffolding.

This separates app-facing Ghostty runtime behavior from the lower-level C interop layer and gives the app a stable Swift module for native view and lifecycle APIs.

## Decision

The implementation will add a Swift-native Ghostty wrapper target responsible for the app-facing Ghostty surface API. `CGhostty` remains as low-level compatibility scaffolding for C interop and pinned metadata.

The wrapper target should expose typed Swift APIs for initialization, surface creation, native view attachment, focus, resize, close, exit status, and appearance translation. `NativeMacADECore` should depend on this Swift wrapper instead of reaching directly into C details for runtime behavior.

## Alternatives Considered

### Alternative 1: Use the existing CGhostty C target as the only native boundary

- **Description**: Replace the current C stub with pinned libghostty calls and keep all Swift runtime wrapping inside `NativeMacADECore`.
- **Pros**: Fewer targets and closer to the current repository shape.
- **Cons**: Mixes app-facing runtime behavior with low-level C interop and makes native view handling harder to isolate.
- **Why rejected**: The selected approach gives the app a clearer Swift-level boundary while preserving `CGhostty`.

### Alternative 2: Vendor Ghostty directly into NativeMacADECore

- **Description**: Remove separate native-boundary targets and call Ghostty from the core module.
- **Pros**: Fewer module hops.
- **Cons**: Pollutes core workspace logic with native terminal interop and makes replacement harder.
- **Why rejected**: The current codebase already benefits from keeping terminal runtime concerns behind separate boundaries.

## Consequences

### Positive

- Creates a stable Swift API for terminal hosting.
- Keeps C interop and pinned metadata isolated.
- Makes future Ghostty API churn easier to contain.

### Negative

- Adds one package target.
- Requires careful dependency wiring in SwiftPM.
- The wrapper still needs to adapt to upstream Ghostty API instability.

### Risks

- Wrapper design could become too broad if it tries to model standalone Ghostty config parity.
- Native view lifecycle details may require iteration once real libghostty APIs are wired.

## Implementation Notes

- Keep the wrapper API minimal and scoped to MVP terminal hosting.
- Do not add Ghostty config parity or pane APIs in this target for the MVP.
- Preserve `CGhostty` for low-level interop and pinned revision checks.
