# ADR-002: Define MVP terminal correctness baseline across common power-user workflows

## Status

Accepted

## Date

2026-06-02

## Context

The Ghostty Terminal Engine PRD already states that terminal correctness is the core product value. During update-mode clarification, the product bar was sharpened: the MVP should validate correctness across interactive TUIs, shell behavior, rendering fidelity, and heavy output. The selected failure standard is strict: any regression versus the current Atelier terminal behavior counts as an MVP failure.

This decision keeps the product scope focused on Ghostty as the terminal experience while making the acceptance bar concrete enough to guide the follow-on TechSpec and task planning.

## Decision

The PRD will add a concrete Terminal Correctness Baseline for the MVP.

The baseline covers:

- interactive TUIs, including vim-style editors, htop-style monitors, tmux-style workflows, and agent CLIs
- shell behavior, including prompts, resizing, copy and paste, keyboard input, and normal command execution
- rendering fidelity, including colors, Unicode, ligatures, and alternate-screen behavior
- heavy output, including logs, long builds, and streaming agent output

Any regression versus the current Atelier terminal behavior in those workflows is treated as an MVP failure. The baseline does not expand the MVP into Ghostty configuration parity or cmux-style workflow features.

## Alternatives Considered

### Alternative 1: Add correctness baseline plus standalone Ghostty parity language

- **Description**: Define the same workflow baseline and use standalone Ghostty behavior as the explicit comparison in common workflows.
- **Pros**: Sets a stronger user-facing parity promise and aligns closely with power-user expectations.
- **Cons**: Can imply broader standalone Ghostty feature parity than the MVP intends to deliver.
- **Why rejected**: The MVP should strengthen acceptance criteria without overpromising full standalone Ghostty parity.

### Alternative 2: Add a separate acceptance phase for power-user workflow validation

- **Description**: Add a dedicated rollout phase before release to validate terminal correctness with representative workflows.
- **Pros**: More rigorous rollout model and clearer release gate.
- **Cons**: Makes the PRD heavier and changes rollout structure when the requested update was to sharpen criteria.
- **Why rejected**: The correctness baseline can be incorporated into the existing MVP and success metrics without adding another phase.

## Consequences

### Positive

- Makes terminal correctness measurable enough for later technical planning.
- Protects current user workflows from regression during the Ghostty switch.
- Keeps the product scope narrow while raising the quality bar.

### Negative

- The MVP has a broader validation burden across several terminal workflow classes.
- Some workflows may need representative examples before implementation work can be planned cleanly.
- Strict regression handling may defer release if parity against current behavior is incomplete.

### Risks

- "Any regression" can become ambiguous without representative workflow examples.
- Power users may still expect standalone Ghostty parity even though the baseline is scoped against current Atelier behavior.
- The validation set could grow unless the MVP examples stay focused on common workflows.

## Implementation Notes

- Use the follow-on TechSpec to define representative workflows and acceptance evidence.
- Keep Ghostty config parity, panes, splits, and cmux-style agent attention out of the MVP unless a later PRD expands scope.
- Treat the current Atelier terminal behavior as the minimum bar and Ghostty as the desired terminal foundation.
