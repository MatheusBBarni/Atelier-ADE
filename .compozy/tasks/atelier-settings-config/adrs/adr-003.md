# ADR-003: File-Authoritative Personal Config Projection

## Status

Accepted

## Date

2026-06-02

## Context

Atelier currently treats SQLite-backed `app_preferences` and `session_shortcuts` as the only durable settings source. The approved PRD requires a personal-global settings file that is portable across machines, user-visible, and reliable for power users. The implementation therefore needs a clear authority model between the external config file and the existing runtime persistence stack.

The user chose a config-file-authoritative design, an XDG-style personal config location, and a V1 apply model that loads on startup and supports explicit manual reload without live file watching. The implementation must preserve the existing startup ordering that loads settings before workspace restore.

## Decision

Supported portable settings will use a **file-authoritative projection model**.

- The canonical config file lives at `$XDG_CONFIG_HOME/atelier/settings.json` when `XDG_CONFIG_HOME` is set, otherwise `~/.config/atelier/settings.json`.
- The config file is the source of truth for supported portable settings.
- SQLite and in-memory runtime state remain the execution cache and compatibility layer for the rest of the app.
- Atelier applies config through one shared flow used by both startup load and explicit manual reload.
- V1 will not watch the file for live changes while the app is running.
- Writes to the config file must be atomic.

## Alternatives Considered

### Alternative 1: SQLite-Authoritative Import/Export

- **Description**: Keep SQLite as the source of truth and treat the file as a derived import/export artifact.
- **Pros**: Fits the existing architecture with less change; preserves a single durable source internally.
- **Cons**: Weakens the portability and dotfile story; makes the file feel secondary; complicates user expectations around manual edits.
- **Why rejected**: The approved product direction treats the file as a first-class user artifact, not a backup format.

### Alternative 2: Bidirectional Mirror With Live Watching

- **Description**: Allow both in-app edits and external file edits to race as peer sources, with live reload while the app runs.
- **Pros**: Feels dynamic and powerful; reacts immediately to external edits.
- **Cons**: Adds conflict resolution, watcher complexity, and harder-to-debug state drift; increases support burden in V1.
- **Why rejected**: V1 should stay deterministic and simple, with explicit reload instead of watcher-driven surprises.

## Consequences

### Positive

- Gives power users a clear, inspectable, portable settings artifact.
- Preserves the PRD’s cross-machine portability promise.
- Reuses the existing runtime store and startup flow instead of replacing them.
- Keeps V1 behavior deterministic by avoiding watcher-driven conflicts.

### Negative

- The app must maintain a projection between the external config file and internal persistence.
- Supported settings now have two representations: external document and runtime cache.
- Manual reload means external edits are not reflected instantly.

### Risks

- **Projection drift** — mitigate with a single shared apply path and atomic config writes.
- **Startup inconsistency** — mitigate by keeping config application ahead of workspace restore.
- **User confusion about stale runtime state** — mitigate with explicit reload UX and clear product language.

## Implementation Notes

- Add a config locator and document codec in `NativeMacADECore` rather than a new app-layer subsystem.
- Keep startup ordering as config load/apply, then theme/runtime refresh, then workspace restore.
- Centralize file-to-runtime projection in `DefaultWorkspaceCommandService` or a closely owned collaborator.
- Manual reload should invoke the same parser, validator, and diagnostics path as startup.
