# ADR-004: Stable Portable Config Schema With Built-In Agent Scope

## Status

Accepted

## Date

2026-06-02

## Context

The current runtime models (`AppPreferences` and `SessionShortcut`) include internal fields such as fixed IDs, UUID references, timestamps, override metadata, and command details that are useful inside the app but are poor candidates for a long-lived user-facing config contract. The PRD also requires portable settings only, which creates additional risk around custom agent profile commands that may not exist on every machine.

The user chose a technical scope that keeps agent portability limited to portable built-ins rather than arbitrary custom command definitions.

## Decision

V1 will expose a **stable external config schema** instead of serializing raw internal models.

- The file format will use symbolic, portable identifiers rather than internal UUIDs or persistence metadata.
- Portable settings will be modeled as a versioned document DTO owned by the config system.
- Agent-profile support in V1 is limited to portable built-in/default profile selection.
- V1 excludes arbitrary custom profile definitions, command paths, launch arguments, secret references, and internal override metadata from the portable config contract.

## Alternatives Considered

### Alternative 1: Serialize Raw Runtime Models

- **Description**: Export `AppPreferences` and `SessionShortcut` directly to the config file with minimal translation.
- **Pros**: Faster to implement; closer to existing persistence types; fewer immediate mapper types.
- **Cons**: Leaks internal fields into the public contract; bakes in UUIDs and metadata; makes future evolution harder.
- **Why rejected**: The external config needs to be stable, human-meaningful, and portable across versions and machines.

### Alternative 2: Include Full Custom Profile Definitions

- **Description**: Put custom labels, commands, and argument definitions in the portable config from day one.
- **Pros**: Broader category coverage; closer to full settings parity; more powerful for advanced users.
- **Cons**: Commands may be machine-specific; portability degrades quickly; support and validation expand well beyond V1 goals.
- **Why rejected**: The approved technical and product scope prioritizes reliable portability over exhaustiveness.

## Consequences

### Positive

- Produces a cleaner long-term public config contract.
- Reduces exposure of unstable or internal-only persistence details.
- Keeps V1 aligned with the portability promise for multi-machine users.
- Simplifies validation and migration compared with full profile portability.

### Negative

- Some power users will not get portable custom command definitions in V1.
- The implementation needs explicit mapping between config DTOs and runtime models.
- The product must explain why some existing settings remain outside the config contract.

### Risks

- **Perceived incompleteness** — mitigate with clear scope documentation and future expansion criteria.
- **Schema drift over time** — mitigate by versioning the external document from the start.
- **Built-in identifier coupling** — mitigate by defining stable symbolic keys intentionally and testing them.

## Implementation Notes

- Prefer symbolic values such as `codex`, `claude`, `opencode`, and `plain` in the external document.
- Keep runtime-only fields such as `updatedAt`, `hasUserOverride`, and `secretRef` out of the file.
- Map config DTOs into `AppPreferences` and supported runtime state through a dedicated translator.
