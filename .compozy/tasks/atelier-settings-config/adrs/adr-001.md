# ADR-001: Single-Scope Personal Settings Config

## Status

Accepted

## Date

2026-06-01

## Context

Atelier already exposes a mature settings surface through its config modal, covering agent profiles, appearance, shortcuts, and app-level behavior. Those settings persist today through a typed SQLite-backed model (`AppPreferences` and `SessionShortcut`) in `~/Library/Application Support/Atelier/Workspace.sqlite`.

The feature idea is to add a file-backed settings config so power users can inspect, version, back up, and move their Atelier personalization across machines. Market research shows this is aligned with current expectations in developer tools and AI-heavy editors, but the same research also shows that advanced tools separate personal configuration from project-shared rules and policy. If Atelier expands into multi-scope configuration too early, it inherits precedence rules, conflict resolution, security exposure, and a broader support burden before validating the core user value.

The council agreed that the highest-leverage V1 is portable personal configuration, not a full configuration platform. The remaining debate centered on how much of the existing modal should become a durable config contract on day one and how much future optionality should be preserved without overbuilding.

## Decision

Atelier V1 will introduce a single user-owned personal-global settings config file for supported personalization data from the existing settings modal.

The V1 config will:

- focus on portable, versioned personal settings
- round-trip with existing settings surfaces only for explicitly supported fields
- use a curated, strictly validated schema for safe and stable personal settings
- clearly define itself as a personal scope, not a project, team, or policy scope

The V1 config will not:

- introduce project-shared, repo-scoped, team-managed, or machine-local override scopes
- store workspace, session, tab, or restore-state data
- become a generic automation, rules, or policy platform
- store secrets or other sensitive values that require protected storage

The schema, naming, and ownership model must preserve a clean personal-scope boundary so future expansion remains possible without promising multi-scope precedence semantics in V1.

## Alternatives Considered

### Alternative 1: Multi-Scope Config Hierarchy in V1

- **Description**: Launch global, project-shared, local-private, or managed scopes in the first release.
- **Pros**: Closer to the most advanced configuration models in the market; supports sharing and richer future workflows immediately.
- **Cons**: Introduces precedence rules, merge behavior, support complexity, policy semantics, and a much larger security surface.
- **Why rejected**: This is a different product from portable personal configuration and would make V1 too broad, risky, and slow.

### Alternative 2: Full Modal Parity as a Durable Config Contract

- **Description**: Make every current settings-modal value file-backed and versionable from day one.
- **Pros**: Strong immediate user story, easy to explain, and closer to the user's original request for complete coverage.
- **Cons**: Turns the full modal into a public compatibility contract, increases migration burden, and exposes unstable or environment-sensitive settings too early.
- **Why rejected**: The council favored a curated supported set with explicit exclusions over versioning the entire current surface before its portability and safety are proven.

## Consequences

### Positive

- Delivers inspectable, versioned, portable personalization for power users now.
- Reuses the existing settings mental model instead of inventing a second configuration product.
- Keeps the trust boundary smaller than a repo-shared or team-managed system.
- Preserves future room for additional scopes without committing to them in V1.

### Negative

- V1 may feel incomplete if some modal values remain excluded from the config contract.
- The product must manage two representations of settings: file-backed config and SQLite-backed persistence.
- Team-sharing and project-specific customization remain unsolved in the first release.

### Risks

- **Users expect full parity immediately** — mitigate with a documented supported-field contract and explicit exclusions.
- **Editable command or agent settings widen the blast radius** — mitigate with strict schema validation, safe defaults, and excluding secrets from the config file.
- **Pressure to add more scopes too early** — mitigate by naming and documenting the V1 feature as personal-global configuration only.

## Implementation Notes

- Use the existing personalization boundary (`AppPreferences` and `SessionShortcut`) rather than exporting the full workspace database.
- Keep workspace/session state outside the config file.
- Reuse the existing settings modal and command-service seam for round-tripping and validation.
- Keep V1 precedence simple: one personal-global config scope plus existing persisted app state, with exact merge semantics defined later in TechSpec.
