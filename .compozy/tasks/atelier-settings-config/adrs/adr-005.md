# ADR-005: Section-Granularity Partial Apply With Diagnostics

## Status

Accepted

## Date

2026-06-02

## Context

The user selected partial apply semantics for mixed valid and invalid config input. The current service APIs, however, are largely all-or-nothing and some settings validate as sets rather than independent leaf fields. Keybindings conflict as a group, and default-profile validity depends on profile availability. A naive field-by-field partial apply would create order-dependent and potentially incoherent runtime state.

The implementation needs a partial-apply model that preserves the user’s choice while fitting the current codebase’s validation patterns.

## Decision

V1 will use **section-granularity partial apply with explicit diagnostics**.

- Independent config sections may succeed or fail independently.
- Related settings within a section validate and apply as a unit.
- A failed section does not block successful sections.
- The apply result must report which sections were applied, skipped, or rejected and why.
- Startup load and manual reload use the same diagnostics model.

## Alternatives Considered

### Alternative 1: All-or-Nothing Apply

- **Description**: Reject the entire config if any supported setting is invalid.
- **Pros**: Keeps runtime state fully coherent; easiest mental model; simplest to implement.
- **Cons**: Too brittle for user-edited config; small mistakes block unrelated valid settings.
- **Why rejected**: The user explicitly chose partial apply semantics for V1.

### Alternative 2: Field-Level Partial Apply

- **Description**: Apply each field independently regardless of relationships to other fields.
- **Pros**: Maximizes salvage of valid input; very fine-grained behavior.
- **Cons**: Creates order dependence and incoherent combinations for grouped settings such as keybindings and profile defaults.
- **Why rejected**: The codebase already validates several settings as sets, and the user approved grouped-section handling for dependent settings.

## Consequences

### Positive

- Preserves user edits that are valid without forcing full-file rejection.
- Fits grouped validation needs for keybindings and profile-related settings.
- Supports better diagnostics and recovery UX.
- Keeps startup and manual reload behavior aligned.

### Negative

- Adds an apply-result model beyond the current exception-only flow.
- Requires clear section definitions and consistent diagnostics semantics.
- Users may need help understanding why some sections applied while others did not.

### Risks

- **Ambiguous diagnostics** — mitigate with structured apply results and clear section names.
- **Order-sensitive bugs** — mitigate by validating/applying through a single orchestrated batch path.
- **Silent partial failures** — mitigate by surfacing rejected sections explicitly in logs and UI feedback.

## Implementation Notes

- Treat sections such as appearance, general behavior, keybindings, and default built-in profile selection as independent apply units.
- Introduce a batch apply result type rather than expressing partial apply through thrown errors alone.
- Reuse the same result model in startup logging, manual reload UX, and automated tests.
