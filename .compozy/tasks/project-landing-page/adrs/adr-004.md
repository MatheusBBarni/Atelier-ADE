# ADR-004: Use a Client-Side GitHub Star CTA Instead of Site Analytics or Build-Time GitHub Metadata

## Status

Accepted

## Date

2026-05-31

## Context

The PRD defines the landing page as trust-first and repo-oriented. During technical clarification, the user chose to emphasize GitHub signals rather than page analytics and specifically requested a button that shows the repository star count and leads visitors to GitHub.

This decision affects both the page’s client behavior and its observability strategy. The main options are: fetch the star count during site build, fetch it client-side in the browser, or avoid dynamic star data entirely. Because the site is small and trust-focused, the implementation should avoid unnecessary backend services or secret management.

## Decision

Implement the primary GitHub CTA as a client-side star-count button that fetches public repository metadata from GitHub at runtime and links visitors directly to the repository.

The MVP will:

- render a stable CTA even before dynamic data loads
- fetch the public star count in the browser without requiring project-owned backend infrastructure
- treat GitHub engagement signals as the primary success indicator instead of adding privacy-invasive page analytics
- keep docs and quickstart links secondary and non-blocking

## Alternatives Considered

### Alternative 1: Build-Time GitHub Metadata Fetch

- **Description**: Fetch repository stars during site build and render the value statically into the page.
- **Pros**: Faster runtime behavior; no client-side API call; avoids browser rate-limit concerns.
- **Cons**: Star counts become stale between deploys; requires build-time data plumbing; disconnects the value shown from real-time GitHub state.
- **Why rejected**: The user explicitly chose a client-side fetch to show live GitHub star data.

### Alternative 2: Traditional Site Analytics Without GitHub Metadata Emphasis

- **Description**: Track engagement using analytics tooling and keep the repo CTA as a standard link.
- **Pros**: Cleaner metrics for page behavior; avoids GitHub API dependency in the browser.
- **Cons**: Adds trust overhead; introduces privacy concerns for a trust-first MVP; moves emphasis away from the repo-centric evaluation path.
- **Why rejected**: The user preferred GitHub-native proof and signals over site analytics.

## Consequences

### Positive

- Reinforces the repo-first strategy technically and visually.
- Avoids the need for server-side infrastructure or secrets for MVP.
- Keeps the page aligned with a trust-first posture by leaning on public GitHub data.
- Makes the primary CTA more concrete than a plain repository link.

### Negative

- Adds client-side dependency on GitHub API availability and browser-side rate limits.
- Creates a small amount of non-static runtime behavior on an otherwise static page.
- Can show a loading or fallback state before the star count resolves.

### Risks

- **GitHub API rate limits or transient failures degrade the star display** — Mitigate by rendering a resilient fallback CTA label and treating the star count as progressive enhancement.
- **Runtime fetch adds avoidable complexity to MVP** — Mitigate by constraining the feature to a single small client script with no extra framework.
- **Observers over-read stars as the only success signal** — Mitigate by documenting that the button is both a proof cue and a repo-entry path, not the sole product metric.

## Implementation Notes

- The page should render correctly even if the star count never loads.
- The client fetch should call only public GitHub endpoints and must not rely on tokens in browser code.
- The button should preserve its navigation value regardless of API success.
