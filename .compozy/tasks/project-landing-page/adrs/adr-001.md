# ADR-001: Docs-First Trailhead Landing Page Scope for V1

## Status

Accepted

## Date

2026-05-31

## Context

Atelier currently relies on `README.md` as its primary public product surface. The product story is stronger than the current public packaging: the repository already shows a native, local-first macOS agentic development environment with persistent projects, project-scoped sessions, restore/resume behavior, agent profiles, and a workflow-speed-first product thesis. However, discovery is weak because the public explanation is thin, the install path is still source-build-heavy, branding is inconsistent across artifacts, and public proof for the "faster workflow" claim is limited.

Market research shows that developer-tool landing pages usually combine an outcome-first hero, immediate product proof, a fast next step, workflow-oriented sections, and trust signals. The same research also shows that developers care deeply about documentation and quickstart quality, abandon tools when setup is difficult, and remain skeptical of AI-tool claims that outrun product reality.

The scope decision is whether Atelier should create a landing page now, how ambitious that page should be, and what CTA posture it should take while the install and trust story is still maturing.

## Decision

Create a minimal V1 landing page now, but treat it as a docs-first trailhead rather than a glossy marketing site.

The page should:

- explain what Atelier is for developers evaluating the project
- lead with the product's real differentiators: native macOS feel, local-first transparency, and faster workflow through clearer project/session context
- include immediate product proof via screenshot or short demo media
- show a concise workflow story that compresses the path from understanding to evaluation
- use documentation as the primary CTA
- keep install or quickstart visible only as a clearly secondary, inspectable next step
- stay honest about current maturity, including early-stage constraints when relevant

The page should not make unverified performance claims, overstate polish, ask for email capture, or pretend the project has a broader trust/commercial surface than it actually does.

## Alternatives Considered

### Alternative 1: Install-First Marketing Page

- **Description**: Build a more conventional developer-tool homepage that pushes install or download as the primary call to action.
- **Pros**: Stronger top-of-funnel push; higher chance of immediate install-starts from high-intent visitors; matches common competitor patterns.
- **Cons**: Over-rotates toward conversion before install trust, branding, and onboarding are mature; increases credibility risk; encourages marketing copy debt.
- **Why rejected**: Current onboarding and proof do not yet support an install-first promise strongly enough.

### Alternative 2: Wait Until Onboarding and Branding Are Cleaner

- **Description**: Delay the landing page until install flow, naming, license, and public proof points are more polished.
- **Pros**: Reduces risk of amplifying rough edges; avoids premature positioning work; lets the public surface launch in a cleaner state.
- **Cons**: Leaves current product discovery weak; slows learning about messaging clarity; keeps README as an underspecified public entry point.
- **Why rejected**: A narrow, honest landing page can improve understanding now and help isolate whether messaging or onboarding is the bigger constraint.

### Alternative 3: Docs-Only Without a Landing Page

- **Description**: Improve only the README/docs flow and skip a dedicated landing page entirely.
- **Pros**: Lowest maintenance; no extra surface area; keeps effort tightly focused on technical documentation.
- **Cons**: Misses the opportunity to provide a clearer orientation layer for new visitors; forces product positioning and workflow explanation into docs alone.
- **Why rejected**: Developers still need a fast, high-level evaluation surface before deciding whether to invest attention in deeper documentation.

## Consequences

### Positive

- Gives Atelier a clearer public explanation without committing to a full marketing site.
- Creates a reusable public story aligned with existing product reality.
- Supports both docs-driven evaluation and downstream install-start measurement.
- Preserves trust by keeping the page narrow, inspectable, and honest.

### Negative

- Adds another public surface that must stay aligned with README, docs, and product naming.
- May still expose onboarding weaknesses more clearly once visitors reach quickstart.
- Limits immediate conversion upside compared with a more aggressive install-first approach.

### Risks

- **Brand drift remains unresolved** — Mitigate by choosing one canonical public name and using it everywhere on the page.
- **Visitors bounce at install despite better messaging** — Mitigate by instrumenting docs click-through, install-start, and first-value activation separately.
- **Trust is weakened by overclaiming speed** — Mitigate by describing workflow compression and transparency instead of unsupported superiority claims.
- **Extra surface area increases maintenance** — Mitigate by keeping V1 static, small, and closely tied to existing docs and product assets.

## Implementation Notes

- V1 should behave like a trailhead: orient the right user quickly, show what is real now, and route them into docs.
- Core sections should stay limited to hero, product proof, workflow/features, differentiators, and CTA.
- Trust-building basics should be present without adding fake maturity: clear links to source/docs, honest maturity/status language, and minimal or no data collection.
- The page should be measured as a funnel step, not as a standalone branding artifact.
