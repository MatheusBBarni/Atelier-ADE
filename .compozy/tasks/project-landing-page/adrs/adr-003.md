# ADR-003: Implement the Landing Page as an Astro Site in /web with GitHub Pages Deployment

## Status

Accepted

## Date

2026-05-31

## Context

The repository is currently a SwiftPM macOS application with no web stack, no package manager for frontend work, and no existing public-site deployment workflow. The PRD defines the landing page as a very small, trust-first public surface, which means the technical implementation must stay lightweight and avoid introducing unnecessary operational burden.

During technical clarification, the user chose to implement the page with Astro rather than with hand-authored static HTML. The user also chose to publish the site through GitHub Pages and, after further clarification, requested that the Astro site live in a new top-level `web/` directory instead of inside `docs/`.

The decision must balance future maintainability, deployment simplicity, and separation from the repo’s Swift application code and mixed-use internal docs folder.

## Decision

Implement the landing page as a minimal Astro site located in a new top-level `web/` directory and deploy it via GitHub Pages using a dedicated GitHub Actions workflow.

The site will:

- keep all web-specific package management and build configuration isolated from the SwiftPM app
- use Astro’s static output mode for a fully pre-rendered site
- treat the landing page as a small standalone web surface rather than mixing it into `docs/`
- reuse existing repository assets where appropriate, either by copying them into Astro-managed locations or referencing stable public assets deliberately
- publish through GitHub Pages using the official GitHub Actions-based deployment flow

## Alternatives Considered

### Alternative 1: Astro Site Under `docs/`

- **Description**: Place the Astro project in `docs/` and deploy it from there.
- **Pros**: Reuses the existing docs asset area; keeps public assets close to current screenshot files; may feel natural for GitHub Pages.
- **Cons**: `docs/` already contains mixed internal planning content; blurs the boundary between site code and documentation artifacts; makes future cleanup harder.
- **Why rejected**: The user explicitly preferred a clean new `web/` folder, which better isolates the site from unrelated repo content.

### Alternative 2: Plain Static HTML/CSS Site

- **Description**: Create a hand-authored static page with no frontend framework.
- **Pros**: Lowest dependency footprint; minimal tooling; easy to inspect.
- **Cons**: Less scalable for future refinement; weaker ergonomics for structured content and asset handling; gives up Astro’s simple static-site workflow after the user explicitly requested it.
- **Why rejected**: The user chose Astro, and Astro adds manageable structure without meaningfully violating MVP scope.

## Consequences

### Positive

- Keeps the web implementation cleanly separated from Swift application code.
- Preserves a lightweight architecture while allowing future site growth.
- Uses a well-supported static-site workflow instead of inventing custom publishing conventions.
- Avoids entangling the public site with the current mixed-use `docs/` directory.

### Negative

- Introduces the repository’s first JavaScript package/toolchain surface.
- Adds a second build path alongside SwiftPM and macOS release automation.
- Requires explicit coordination between public-site assets and existing repo assets.

### Risks

- **The web folder becomes broader than the MVP needs** — Mitigate by keeping the Astro site minimal: one route, minimal components, minimal client code.
- **Pages deployment settings drift from repo expectations** — Mitigate by documenting the deployment path and using a dedicated workflow.
- **Asset duplication creates maintenance overhead** — Mitigate by defining clear ownership for site assets and reusing only the small set required for MVP.

## Implementation Notes

- The Astro site should begin with the smallest useful structure: config, a single page route, minimal styles, and only the assets needed for MVP.
- GitHub Pages should use an Actions-based deployment rather than a manual branch-publish flow.
- The `web/` directory should remain intentionally isolated from Swift packages and internal planning docs.
