# ADR-004: Canonicalize Order with Existing Fields and Atomic Batch Persistence

## Status

Accepted

## Date

2026-05-31

## Context

The codebase already persists project order with `Project.sortIndex`, tab order with `Tab.ordinal`, and restore order with `RestoreSnapshot.tabOrder`. The PRD requires immediate durable persistence after each successful reorder. The current persistence layer, however, is oriented around single-row saves and tab ordinals are constrained by `UNIQUE(session_id, ordinal)` in SQLite.

The design therefore needs an authoritative persistence strategy that avoids introducing a second priority model while also preventing transient uniqueness conflicts and relaunch drift.

## Decision

The implementation will reuse the existing persisted order fields and make them canonical.

- `Project.sortIndex` remains the source of truth for project order.
- `Tab.ordinal` remains the source of truth for selected-session tab order.
- `RestoreSnapshot.tabOrder` will be regenerated immediately from the updated store after each tab reorder and treated as derived state, not a second editable source of truth.

The persistence layer will gain atomic batch reorder operations that rewrite all affected project or session-tab rows in one transaction. No schema change is required for MVP.

Additional normalization rules:

- Project reorder will assign dense unique `sortIndex` values so recency is no longer used to break ties inside a user-authored order.
- Tab reorder will assign conflict-free dense ordinals across the session.
- If persisted tab metadata exists for tabs not currently visible in the live store, those tabs will be appended after the reordered visible set while preserving their relative order.

## Alternatives Considered

### Alternative 1: Add separate priority metadata

- **Description**: Introduce new priority fields or records and leave current ordering fields as-is.
- **Pros**:
  - Separates user-authored order from existing ordering semantics.
  - Could support future pinned or grouped priority systems.
- **Cons**:
  - Adds new storage concepts before they are needed.
  - Increases migration and restore complexity.
  - Creates two competing models for visible order in MVP.
- **Why rejected**: Existing fields already model the behavior the feature needs, so a second priority model would be unnecessary abstraction.

### Alternative 2: Update only restore snapshot or defer persistence

- **Description**: Treat reorder as a runtime-only change until a later activation or shutdown event, or persist only snapshot order.
- **Pros**:
  - Smaller initial persistence changes.
  - Potentially less write volume during interaction.
- **Cons**:
  - Weak durability guarantee.
  - Relaunch order can drift from runtime order.
  - Snapshot-only persistence leaves ordinal semantics inconsistent.
- **Why rejected**: The PRD requires order to survive normal use and return flows reliably, which demands immediate authoritative persistence.

## Consequences

### Positive

- Avoids schema churn for MVP.
- Keeps one clear source of truth for visible order.
- Makes restore behavior consistent with normal in-app ordering.

### Negative

- Requires new transactional batch persistence code.
- Forces the implementation to define policy for hidden persisted tabs and dense index normalization.

### Risks

- **Transaction risk**: partial writes could corrupt ordering. **Mitigation**: persist the full affected set and snapshot in one transaction.
- **Hidden-state risk**: persisted-but-not-visible tabs could reappear unpredictably later. **Mitigation**: preserve their relative order and append them after reordered visible tabs.

## Implementation Notes

- Do not persist tab swaps as row-by-row ordinal exchanges.
- Regenerate restore snapshot order from the authoritative post-reorder store state.
- Reject reorder payloads that omit visible items or include unknown identifiers.
