# ADR-005: Scope Tab Reordering to the Existing Session-Scoped Mixed Tab Strip

## Status

Accepted

## Date

2026-05-31

## Context

The PRD requires the MVP to include tab reordering, but the shipped application does not have a vertical tab surface. Instead, the product renders a horizontal tab strip for the currently selected session, and that strip already mixes terminal tabs and file tabs in one ordered namespace.

The technical design must decide whether to add a new surface, split tab behavior by kind, or stay inside the existing strip and model.

## Decision

MVP tab reordering will be implemented in the existing horizontal `TabChromeView` for the currently selected session.

The feature will reorder all visible session tabs together, including both terminal and file tabs, using the existing shared tab namespace. The TechSpec will not introduce a new vertical tab surface, cross-session tab ordering, or separate ordering rules per tab kind.

## Alternatives Considered

### Alternative 1: Add a new vertical tab surface

- **Description**: Build a new vertical tab list to match the original “move vertically” framing more literally.
- **Pros**:
  - Aligns more directly with the earlier wording of the idea.
  - Could create a stronger future foundation for more advanced tab management.
- **Cons**:
  - Adds a new navigation surface to MVP.
  - Broadens scope beyond the current shipped workspace model.
  - Requires users to learn a second tab interaction surface.
- **Why rejected**: The MVP should extend the current architecture rather than add a second surface just to satisfy one interaction metaphor.

### Alternative 2: Reorder only terminal tabs or only file tabs

- **Description**: Limit reordering by tab kind instead of treating the strip as one shared ordered set.
- **Pros**:
  - Narrower implementation scope.
  - Avoids some mixed-kind behavioral questions.
- **Cons**:
  - Conflicts with the current single-strip model.
  - Produces inconsistent user rules inside one visible tab surface.
  - Risks surprising users when some visible tabs can move and others cannot.
- **Why rejected**: The strip is already one ordered session surface, so MVP should keep one consistent rule across all visible tabs.

## Consequences

### Positive

- Reuses the existing tab surface users already understand.
- Keeps tab scope aligned with the current selected-session model.
- Avoids inventing separate behavior for terminal and file tabs.

### Negative

- The UX will not literally be a vertical tab move experience.
- Mixed terminal/file reordering slightly widens testing needs compared with a terminal-only slice.

### Risks

- **Expectation mismatch risk**: prior wording may imply a different surface than the shipped implementation. **Mitigation**: document that MVP uses the current tab strip and keep product copy aligned to the existing surface.
- **Mixed-kind risk**: file and terminal tabs may expose edge cases in selection and restore. **Mitigation**: cover mixed-tab reorder and relaunch scenarios in integration tests.

## Implementation Notes

- Scope tab reorder to `store.tabsForSelectedSession` only.
- Do not add cross-session tab movement or workspace-wide tab ordering in MVP.
- Preserve existing selection behavior after reorder unless the selected tab becomes unavailable.
