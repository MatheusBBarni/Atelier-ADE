# ADR-003: Command-Owned Reorder Operations for Projects and Tabs

## Status

Accepted

## Date

2026-05-31

## Context

Project and tab ordering are rendered by two custom SwiftUI surfaces in `ContentView.swift`: a vertical project sidebar and a horizontal session tab strip. Neither surface currently owns persistence or durable workspace mutation. The existing architecture routes state-changing behavior through `WorkspaceCommandService` and `DefaultWorkspaceCommandService`, which already coordinate store updates, persistence writes, and restore snapshot updates.

The feature needs drag-and-drop style interactions in the UI, but it also needs immediate durable persistence and consistent behavior across relaunch and restore. A view-local mutation path would duplicate business rules, make persistence ordering harder to audit, and create divergence between the two surfaces.

## Decision

Reorder operations will be owned by `WorkspaceCommandService` and implemented in `DefaultWorkspaceCommandService`.

The MVP will add explicit surface-specific commands rather than a generic ordering abstraction. The command layer will accept fully ordered identifier lists from the UI, validate them against the current store, normalize authoritative ordering, persist changes atomically, and then restore the updated store state into the runtime.

Planned command shape:

- `reorderProjects(_ orderedProjectIDs: [UUID])`
- `reorderTabs(sessionID: UUID, orderedVisibleTabIDs: [UUID])`

SwiftUI views will remain thin interaction shells responsible only for drag/drop state and for passing the resulting ordered IDs into the command layer.

## Alternatives Considered

### Alternative 1: Introduce a generic ordering service

- **Description**: Build a shared ordering coordinator used by projects, tabs, and future reorderable surfaces.
- **Pros**:
  - Could reduce duplication if many reorderable surfaces appear later.
  - Centralizes generic move and normalization logic.
- **Cons**:
  - Introduces abstraction before real extension pressure exists.
  - Obscures meaningful differences between project ordering and tab ordering.
  - Adds more indirection to an MVP feature with only two surfaces.
- **Why rejected**: The current feature does not justify a generalized framework. Surface-specific commands are clearer and more aligned with YAGNI.

### Alternative 2: Let views mutate the store directly

- **Description**: Keep reorder logic in SwiftUI views and update the store without command-layer ownership.
- **Pros**:
  - Fewer new command APIs.
  - Faster to prototype interaction behavior.
- **Cons**:
  - Splits persistence rules across UI and core layers.
  - Makes restore and transactional durability harder to reason about.
  - Increases the chance that project and tab surfaces drift in behavior.
- **Why rejected**: Durable order is a workspace concern, not a view concern. The command layer is the existing owner for persisted user actions.

## Consequences

### Positive

- Keeps mutation ownership in the same layer that already coordinates durable workspace changes.
- Lets both surfaces share persistence and validation rules without inventing a generic framework.
- Makes transactional durability, logging, and testing easier to centralize.

### Negative

- Adds new command methods and more logic to `DefaultWorkspaceCommandService`.
- Leaves two bespoke UI interaction implementations because the sidebar and tab strip are not one reusable list primitive.

### Risks

- **Command bloat risk**: the command layer may grow into a broad catch-all. **Mitigation**: keep APIs narrow and surface-specific.
- **Validation risk**: ordered ID payloads could be incomplete or malformed. **Mitigation**: reject invalid reorder payloads before mutating persistence.

## Implementation Notes

- Commands should accept ordered IDs rather than view-local index deltas.
- The command layer should preserve selection unless the current item becomes unavailable.
- Persistence and snapshot updates should happen in one coordinated command path per reorder operation.
