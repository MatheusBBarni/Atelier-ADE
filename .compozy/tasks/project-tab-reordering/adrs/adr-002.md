# ADR-002: Dual-Surface MVP for Project and Tab Reordering

## Status

Accepted

## Date

2026-05-31

## Context

The PRD for Project and Tab Reordering needs a clear product approach before the document is written. Earlier idea work narrowed V1 to projects only because project ordering is structurally cleaner and easier to trust. However, the current PRD discovery produced a different product signal.

The user wants the first release to serve both heavy multi-project users and AI-heavy session jugglers. The primary outcome is calmer project re-entry, but tabs are still considered a first-class part of the promise rather than a later follow-up. Market research also shows that tab reordering is a baseline expectation in serious desktop and developer tools, while custom project ordering is less standardized and more differentiating. The product question is therefore not whether tabs matter, but whether the PRD should describe a safer projects-only wedge or a tighter dual-surface release.

## Decision

The PRD will use a **dual-surface MVP** approach.

The first release will include both project reordering and tab reordering in the same product story. The PRD will frame calmer project re-entry as the primary user outcome and faster in-session tab recovery as the supporting outcome. The scope will stay deliberately narrow: no pinning, favorites, grouping, or broader workspace-priority controls in the MVP.

## Alternatives Considered

### Alternative 1: Projects-first wedge

- **Description**: Make project reordering the only first-release promise and describe tab reordering as the next planned expansion.
- **Pros**:
  - Simpler first-release story.
  - Lower trust burden on the MVP.
  - Cleaner fit with earlier idea-stage scope analysis.
- **Cons**:
  - Leaves an obvious user expectation unmet in the tab layer.
  - Conflicts with the user’s desire to keep tabs equal in the first release.
  - Risks making the feature feel incomplete for AI-heavy users who live in active tab workflows.
- **Why rejected**: The chosen audience and user direction require tabs to be part of the first product promise, not just a future note.

### Alternative 2: Workspace priority suite

- **Description**: Expand the feature into a broader priority system across projects, tabs, and adjacent controls such as pinning or favorites.
- **Pros**:
  - Stronger strategic narrative around workspace control.
  - More differentiated long-term product posture.
  - Could unify multiple priority behaviors under one umbrella.
- **Cons**:
  - Too much scope for the MVP.
  - Adds adjacent features the user explicitly does not want in the first release.
  - Increases document complexity before the core manual-ordering promise is proven.
- **Why rejected**: The MVP should validate manual reordering directly before broadening into a larger prioritization system.

## Consequences

### Positive

- Produces a more complete first-release story for users who move between projects and active tabs all day.
- Aligns the PRD with the user’s explicit desire to keep both surfaces in the MVP.
- Lets the product combine a differentiating project-layer value with a table-stakes tab-layer expectation.

### Negative

- Increases trust pressure because two surfaces must feel stable in the first release.
- Creates tension with earlier idea-stage guidance that preferred a projects-only slice.
- Raises the risk that one weaker surface could dilute the perceived value of the whole feature.

### Risks

- **Trust risk**: if custom order does not persist reliably, the feature loses credibility quickly. **Mitigation**: make durable persistence a central product requirement.
- **Scope risk**: the feature could expand into pinning, grouping, or other priority tools too early. **Mitigation**: keep the MVP strictly focused on manual ordering only.
- **Narrative risk**: project value may be stronger than tab value, causing uneven user impact. **Mitigation**: define separate success measures for project re-entry and tab-level navigation improvement inside one shared PRD.

## Implementation Notes

- This ADR sets product scope and positioning for the PRD.
- Technical design choices remain out of scope for this document and belong in the later TechSpec.
